[0:01-0:12] 我们直接来看核心问题：如何让外部的 Python 环境，比如用 VS Code 写的高版本 Python 代码，和大 QMT 这个交易执行平台顺畅地对话？这本质上是一个**进程间通信**的问题。
[0:15-0:20] 大家看这张图，非常清晰地展示了我们的目标架构。
[0:20-0:49] 左边是你的开发环境，用着最新的 Python 版本，跑着 VS Code，负责复杂的模型计算和信号生成；右边是大 QMT，它运行在一个特定的**嵌入式 Python 环境**里，主要职责是接收来自左边的指令并执行交易。注意看箭头：单向的是信号发送，双向的是状态同步（比如查询持仓、查询订单）。这种分离架构的好处显而易见：**计算和执行解耦，便于管理和扩展**。
[0:49-1:01] 要实现这种通信，业界有几种主流方案。今天我们重点拆解三种：**文件桥接、HTTP 桥接和 Redis 桥接**，它们各有特点，适用于不同的场景。

## 方案一：文件桥接 —— 零依赖的"留言板"
[1:03-1:28] 先说最简单粗暴的一种。你可以把它想象成一个物理留言板：你的策略程序想下单，就在指定的文件夹里写个小纸条（比如"我要买 XX 股票，一手"），然后大 QMT 这边派个"小弟"定时去文件夹门口看看有没有新纸条，看到了就读出来执行，执行完再在另一个文件夹（比如 done）里打个勾。
[1:28-1:41] 优点是什么？**简单**！不需要任何额外的服务，只要你的电脑能读写文件就行。缺点也很明显：那个"小弟"查岗是有间隔的，万一你写完纸条小弟正好去"吃饭"了，就有延迟。
[1:55-2:30] 具体怎么落地？一个成熟的做法是用目录来管理这些"纸条"。创建几个专门的文件夹：**pending** 放待处理的订单，**done** 放成功执行的，**failed** 放失败的，再加两个：**query** 放你的查询请求，**reply** 放 QMT 返回的查询结果。这样一套组合拳下来，基本的请求-响应闭环就形成了：外部程序把信号写到 pending，QMT 处理完根据结果写到 done 或 failed；需要查询时写 query，QMT 处理后写 reply。结构清晰，职责分明。
[2:31-3:17] 这张流程图更直观：左边是你写的 Python 代码，调用一个 **send_order** 函数，函数内部把订单信息打包成 JSON 格式，写进 pending 目录下的一个文件里，比如 **buy_600519.json**。右边大 QMT 里有个定时任务，像个巡逻兵一样每隔一段时间（比如 3 秒）扫描一下 pending 目录，发现新文件就读出来、解析 JSON，然后调用 **passorder** 这样的底层函数去执行下单。执行成功就在 done 目录下创建同名文件标记状态为 ok，失败就在 failed 目录下创建。最后不管成不成功，都把 pending 里的原始文件删掉，避免重复处理——这就是典型的**生产者-消费者模式**。
[3:18-4:42] 看点实际代码。Python 端定义了一个 **QtSignalBridge** 类，初始化时自动创建刚才说的 pending、done、failed、query、reply 五个目录。核心方法 send_order 接收股票代码、买卖方向、价格、数量等参数，生成唯一订单 ID，用 json.dumps 打包写入 pending 下以订单 ID 命名的 JSON 文件。QMT 端关键在于使用 **run_time 函数**设置定时任务（比如每 3 秒执行一次 process_signals）：找到 pending 下所有 JSON 文件，逐个解析，action 等于 buy 就调 passorder 下单，等于 sell 就执行卖出；完成后构造结果字典写入 done 目录（`json.dump(result, f)`），并删除已处理的 pending 文件。注意这里用的是 **run_time 定时任务而不是行情回调 handlebar**——这样即使没有行情数据进来，信号也能被及时处理。
[4:42-5:27] 光下单还不够，我们可能还需要查询持仓、资产或委托情况，文件桥接也能搞定，通过 query 和 reply 目录实现反向通信。比如你想查持仓，就在 query 目录下写一个 **get_positions_123.json** 文件，QMT 的定时任务扫描到后调用 **get_trade_detail_data** 这样的函数获取数据，把结果写回 reply 目录下的 reply_get_positions_123.json。你的 Python 程序再去轮询 reply 目录，就能拿到最新持仓。用完记得把 reply 里的文件也删掉。
[5:27-6:10] 总结一下文件桥接的优缺点。优点：**零外部依赖**，只要系统有文件系统就能跑；每个信号都是独立的 JSON 文件，出了问题查日志特别方便，**可追溯性好**；实现非常简单，几分钟就能搞定；而且支持双向通信。缺点：只能在本地跑，没法跨机器；因为是轮询机制，存在时间间隔，可能有**延迟盲区**；读写文件比纯内存操作慢（SSD 下差别不大但终究是有的）；还有个坑——**编码问题**，Python 端常用 UTF-8，而 QMT 环境可能是 GBK，不一致会导致乱码。
[6:10-6:47] 所以文件桥接适合哪些场景？如果你做的是**日线、小时线这种低频策略**，或者只是想快速验证一个想法又不想装任何东西，它是最佳选择；对追求零依赖、快速上手的个人研究者非常友好。但如果你的策略是 **Tick 级别**或分钟级别的高频交易、对延迟极其敏感，文件桥接的毫秒级延迟和轮询盲区就不合适了；需要部署在多台机器、开发环境和 QMT 不在同一台机器上，文件桥接也帮不上忙。

## 方案二：HTTP 桥接 —— 标准的"远程遥控器"
[6:47-7:17] 第二种方案。你可以把它想象成一个标准的远程遥控器：QMT 在后台启动一个 Web 服务器，监听某个端口，对外提供一系列 **RESTful API** 接口（比如 POST /api/order/buy 下单、GET /api/holding 查询持仓）。外部程序只需像调用普通网页一样发送 HTTP 请求，就能直接控制 QMT 的行为。
[7:17-7:44] 好处是**标准、通用**，任何语言写的程序都能对接，天然支持跨机器通信。缺点：启动 Web 服务器会阻塞 init 函数，需要小心处理生命周期；要占用一个端口避免冲突；想从公网访问还需要做端口映射或内网穿透。
[7:38-8:25] 技术上怎么实现？核心就是在 QMT 的 init 函数里启动一个 Web 服务。QMT 内置的 Python 环境自带 **Tornado** 库（轻量级 Web 框架，非常适合）。用 Tornado 注册路由：/api/order/buy 对应下单逻辑，/api/holding 对应查询持仓；把这些路由注册到一个 Application 对象，让应用监听一个端口（比如 **10086**），最后调用 **IOLoop.current().start()** 启动事件循环，Web 服务就开始运行了。这样外部程序就可以通过 http://localhost:10086/api... 这样的 URL 来访问 QMT 的功能。
[8:25-9:12] HTTP 桥接最大的优点是**通用性和跨平台能力**：标准 HTTP 协议，无论 Java、Go、JavaScript 还是其他语言都能轻松对接；天然支持请求-响应模式，双向通信非常方便。缺点同样突出：启动 Tornado 的 IOLoop.start 会**阻塞 init 函数**——Web 服务启动后 init 就不会往下走了，可能影响 QMT 的初始化流程，需要仔细设计；要管理好端口号别跟别的程序冲突；从外面访问涉及网络穿透；作为网络通信还要考虑延迟、超时重试等问题。
[9:12-9:53] 什么时候选 HTTP 桥接？如果你的**开发环境和 QMT 不在同一台机器**（比如你在 Mac 上写代码，QMT 在 Windows 服务器上跑），HTTP 桥接是必须的；想让**多个客户端共享同一个 QMT 实例**，或者搞团队协作、前后端分离，也非常合适；特别是需要**非 Python 语言接入**时（用 JavaScript 或 Go 写前端/中间层），HTTP 桥接是唯一的选择。当然只是本地单机跑，文件桥接显然更简单。注意：从公网访问一定要做好安全防护和内网穿透配置。

## 方案三：Redis 桥接 —— 超高速的"共享白板"
[9:53-10:40] 最后一种，也是**性能最强**的方案。你可以把它想象成一块超高速的共享白板。Redis 是一个**内存数据库**，读写速度非常快，达到**微秒级别**。外部程序把交易信号写入 Redis，大 QMT 从 Redis 读取。最大的优势就是快——特别是使用 Redis 的 **Pub/Sub 发布订阅模式**时，几乎是实时推送，没有轮询的延迟。缺点：需要额外部署和维护一个 Redis 服务（运维成本），Redis 默认不支持 Windows 需要额外安装，服务挂了通信就中断。适合对延迟要求极高的场景，比如 Tick 级别的高频交易。
[10:40-11:25] 原理相对简单。外部程序通过 Redis 的 **SET** 命令把交易信号（JSON 格式）写入一个键，比如 **trade_signal**。大 QMT 端两种读取方式：一是**轮询模式**，定期用 GET 查这个键，有值就读出处理，处理完最好 DEL 删除；二是**推送模式**，利用 **SUBSCRIBE** 订阅一个频道（比如 **signal_channel**），外部程序用 **PUBLISH** 向频道发布消息时，Redis 主动推送给所有订阅者，QMT 立刻收到信号，无需轮询等待——**推送模式是 Redis 桥接的核心优势所在**。
[11:25-12:05] 两种消费模式差别很大：轮询就像隔几分钟去邮箱看有没有新邮件，延迟完全取决于轮询间隔（1 秒一次最坏延迟就是 1 秒）；订阅就像订了新闻推送服务，几乎是即时的，延迟可以做到**毫秒级甚至更低**。对高频交易来说，这种毫秒级差异可能就是**生死线**。所以强烈推荐 Redis 的 Pub/Sub 推送模式。
[12:05-12:57] 代码层面也很直观。Python 端先建立 Redis 连接：轮询模式直接 `r.set("trade_signal", signal)` 存进去；推送模式用 `r.publish("signal_channel", signal)` 发布到频道。大 QMT 端（推送模式）创建连接后用 `pubsub = r.pubsub()` 创建发布订阅对象，`pubsub.subscribe("signal_channel")` 订阅目标频道，然后进入循环 `for msg in pubsub.listen()`：msg['type'] 是 'message' 时，msg['data'] 就是收到的信号内容，解析后立即执行交易逻辑，响应速度非常快。
[12:57-13:44] Redis 桥接优缺点总结。优点：**快**——纯内存操作，延迟极低（微秒级）；Pub/Sub 推送模式几乎没有延迟盲区，真正实时；本身支持双向通信（List 作队列、Channel 推送）；还支持持久化，服务重启数据不丢。缺点：要维护一个 Redis 服务（运维负担）；Windows 上部署比 Linux/Mac 更麻烦；Redis 宕机整个通信链路就断，需要容错和恢复机制；相比文件桥接引入了额外的基础设施。
[13:44-14:15] 适合什么场景？毫无疑问是**对延迟要求极高的 Tick 级别高频交易**；或者团队已有成熟的 Redis 基础设施、本来就需要高性能消息队列。但如果只是快速验证日线策略、追求零依赖快速上手，Redis 桥接就有点**杀鸡用牛刀**了。

## 三方案横向对比
[14:15-15:26]
| 维度 | 文件桥接 | HTTP 桥接 | Redis 桥接 |
|---|---|---|---|
| 额外依赖 | 最干净 | QMT 自带 Tornado | 需额外 Redis 服务 |
| 通信方式 | 轮询 | 请求-响应 | 轮询或推送 |
| I/O 延迟 | 最慢 | 较快 | 最快 |
| 端到端最坏延迟 | 轮询间隔+I/O 时间 | 请求处理时间 | 轮询看间隔；**推送几乎实时** |
| 跨机器 | ✗ | ✓（需处理公网访问） | ✓（需网络可达） |
| 双向通信 | ✓ | ✓ | ✓（List 队列/Channel 推送） |
| 可追溯性 | 最好（每信号一文件） | 需自己加日志 | 默认不持久化，最差 |
| 运维复杂度 | 最低 | 需配置维护 | 需配置维护 |
| 上手难度 | 最容易 | 需网络知识 | 需网络/数据库知识 |

## 落地提醒：八个常见的坑
[15:50-17:30]
1. **编码不一致**：Python 默认 UTF-8，QMT 可能是 GBK——读写文件务必统一编码，否则一堆乱码。
2. **信号重复执行**：网络波动或程序异常导致信号文件没被正确删除，下次启动又读一遍就会重复下单。解决办法：文件名唯一性、内存中维护已处理信号集合、或确保消费后立即删除文件。
3. **定时任务未触发**：文件桥接中 QMT 策略没正常运行、或 run_time 函数没正确注册，定时任务就不会执行。
4. **init 被阻塞**：主要是 HTTP 桥接，IOLoop.start 是死循环，会阻塞后续代码，需要理解 QMT 的生命周期管理。
5. **端口冲突**：HTTP 和 Redis 都要占端口，被别的程序占用就起不来。选不常用端口或允许用户自定义配置。
6. **跨公网访问**：HTTP 和 Redis 从外面访问都需要固定 IP + 端口映射，或者用 **frp、ngrok** 这样的内网穿透工具。
7. **Redis 服务宕机**：通信会中断，可通过配置持久化选项（RDB/AOF）和守护进程自动重启来缓解。
8. **信号文件堆积**：文件桥接处理不当会留下大量 done/failed/reply 文件占满磁盘，**定时清理超过 24 小时的旧文件**是好习惯。

## 总结
[17:31-17:47] 文件、HTTP、Redis 三种桥接方案各有千秋，没有绝对的优劣之分：
- **文件桥接**：简单粗暴零依赖，适合快速验证和低频策略
- **HTTP 桥接**：标准通用，跨语言跨机器，适合局域网协作和团队开发
- **Redis 桥接**：性能极致，推送模式实时性高，是高频交易的首选

关键在于根据你的实际需求做出选择。记住：没有最好的，只有最适合的。希望这些内容能帮助大家更好地搭建自己的量化交易系统。
